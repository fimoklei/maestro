- **2026-08-09 · tooling/partial-commit-needs-add-first** — `git commit -m … -- <paths>` is the way to commit only what you wrote while leaving unrelated staged and dirty work alone, but on untracked paths it fails with `error: pathspec '<path>' did not match any file(s) known to git` — including on an unborn branch, where the whole tree is untracked. Running `git add -- <paths>` first makes the same partial commit succeed, still committing only those paths and leaving everything else staged. Measured on git 2.50.1. → Stage the exact paths, then partial-commit the exact paths; never read the pathspec error as "partial commits do not work here", and never fall back to a bare `git commit`, which would sweep up the user's own staged work.
- **2026-08-06 · tooling/empty-repo-hides-its-default-branch** — On an empty repository `git ls-remote --symref <url> HEAD` prints zero lines and exits 0, so it cannot distinguish "no default branch" from "cannot tell", while `git clone` does learn the unborn branch (protocol v2) and checks it out, beating the client's `init.defaultBranch`. `refs/remotes/origin/HEAD` is absent after that clone and stays absent after the first push; only `git remote set-head origin -a` writes it. Measured on git 2.50.1 against GitHub and a local bare repo. → Read an empty repository's default branch from the clone (`git symbolic-ref HEAD`), never from `ls-remote`, and call `set-head -a` after the first push. Capture: `docs/research/552-empty-repo-and-scaffold-shape.md`.
- **2026-08-06 · tooling/bare-remote-is-stricter-than-github** — Pushing a branch other than the advertised unborn one into an empty repository diverges: GitHub adopts the pushed branch as the repository's default, while a local bare remote leaves `HEAD` dangling at a branch that was never created and reports `HEAD branch: (unknown)` forever. Measured on git 2.50.1. → A bare remote stands in for GitHub for clone, `origin/HEAD` and same-branch push, but its outcome for a *different*-branch push is not GitHub's; never read one as the other.
- **2026-08-03 · tooling/git-remote-get-url-resolves-inteadof** — `git remote get-url origin` returns the URL after `url.<other>.insteadOf` rewriting; `git config --get remote.origin.url` returns what the author configured. Measured on git 2.51: with the rewrite in place the two disagree, and reading the rewritten one made the Harness view name a local mirror path as its GitHub origin. → Read the configured URL for anything shown to the author or used as repository identity, and the rewritten one only when you need the URL git will actually reach. The same rewrite is what lets an integration test give a temp clone a real `github.com` origin while staying offline.
