# What APM 0.35.0 supports for acting on one user-level folder (issue #1769)

Date: 2026-11-02. apm **0.35.0** (tag `v0.35.0`, `17a2fc4`), compared with
the pinned **0.32.0** (`scripts/bootstrap.mjs:8`). Builds on
[1550-per-folder-selection.md](1550-per-folder-selection.md) and
[1551-user-level-folders-and-detection.md](1551-user-level-folders-and-detection.md).
Paths below are relative to `src/apm_cli/` at `v0.35.0`.

**Method.** Source: `microsoft/apm` cloned at the tag, diffed against
`v0.32.0`. Measured: apm 0.35.0 from PyPI in its own venv, and the 0.32.0 on
`PATH`, each against a `realpath`ed sandbox `HOME` with a neutral cwd. Fixture:
`github.com/fimoklei/harness`, Selection `grilling, workflow-ship`, at `v0.4.0`,
then `v0.4.1` (which changes only `workflow-ship/SKILL.md`). Every command used
Maestro's form: write `skills:`, then install the root ref with one `--skill` per
name and `-g -t <tools>`. "(measured)" marks a run on both versions unless
noted. "(source)" marks a claim read from code. A bare `#N` after the title
is a `microsoft/apm` pull request or issue. Nothing here was applied to
the code, the glossary, the ADRs or `docs/apm-behavior.md`.

## Answer

**No, for all three actions.** APM 0.35.0 still keeps one ref and one flat
`skills:` list per dependency, with no folder dimension. The 0.32.0 answer of
#1550 stands.

| Action on one folder | Recorded state | On disk | Lasts? |
|---|---|---|---|
| Install a skill to `~/.agents/skills` only | No | Yes, with `-t codex` | Until the next install that names Claude |
| Update `~/.agents/skills` to a newer release only | No | Yes, with `-t codex` | Same, and the lockfile says the newer release for both folders |
| Remove a skill from `~/.agents/skills` only | No | Yes, with `-t codex` | Same |

A narrowed `-t` changes one folder on disk and leaves the other one alone. APM
records no folder-level intent for it: `apm.yml`, `skill_subset` and
`resolved_ref` describe the narrowed run's result for **every** folder. So the
next install with `-t claude,codex` makes both folders equal again. This is
APM's design, not a gap it closes by accident (#3313: "A target-only install
must preserve unprocessed claims").

## Evidence

### The manifest has no folder dimension (source)

- **Unchanged since 0.32.0.** `git diff v0.32.0 v0.35.0` is empty for
  `models/dependency/object_fields.py` and `models/dependency/subsets.py`. A git
  entry accepts `alias, allow_insecure, git, path, ref, skills, targets, type`
  (`object_fields.py:13-24`); `skills:` is one sorted list
  (`subsets.py:36-56`).
- **One repository gives one entry.** `get_unique_key` still ignores `skills`
  and `targets` (`models/dependency/reference.py:366-389`). The new `replace:`
  block (#3309, `models/dependency/replacement.py`) redirects a source and keeps
  the original key (`reference.py:376-377`). It adds no folder choice.
- **One skill filter for every folder.** For a root package, the integrator
  builds one `name_filter` (`integration/skill_integrator.py:1054`) and passes
  it to every active target in one loop (`:1084-1124`). A folder shared by two
  targets is written once (`:1090-1099`).
- **No upstream plan.** No open issue or discussion in `microsoft/apm` asks for
  a per-target `skills:` list or `apm uninstall -t` (searches for "per-target",
  "uninstall target", "dependency targets field", and discussions, 2026-11-02).
  The nearest is #2606, per-dependency `targets` for MCP entries.

### Update one folder (measured)

Baseline `v0.4.0` under `-t claude,codex`, then
`apm install …harness#v0.4.1 --skill grilling --skill workflow-ship -g -t codex`:

- `~/.agents/skills/workflow-ship/SKILL.md` moves to `v0.4.1`.
  `~/.claude/skills/workflow-ship/SKILL.md` stays at `v0.4.0`.
- The lockfile has one entry at `resolved_ref: v0.4.1`. The `.claude` rows keep
  their `v0.4.0` hash, which matches the disk, so a hash check sees no edit.
- `apm outdated -g` shows one row, `Current v0.4.1`. Nothing shows that Claude's
  copy is a release behind.
- The next `-t claude,codex` install at `v0.4.1` brings `.claude` up.

The cause is `core/deployment_state.py:527-539`: a row is stale only when its
target is active, or when the target is known, absent from `apm.yml`'s
`targets:`, and not still held by a target this run skipped
(`DeploymentIntent.unprocessed_claims`, `:118`). Claude is declared and
inactive, so its rows stay.

### Install or remove for one folder (measured; install on 0.35.0 only)

- **Remove.** Write `skills: [grilling]`, then install with `--skill grilling`
  and `-t codex`. `.agents/skills/workflow-ship` is deleted. `.claude/skills/workflow-ship`
  stays on disk and in `deployed_files`, while `skills:` and `skill_subset`
  already say `[grilling]`. The next `-t claude,codex` install deletes the
  Claude copy.
- **Install.** Add `--skill show-me` with `-t codex`. Only `.agents` gets it,
  but `skills:` lists it for both. The next `-t claude,codex` install writes it
  to `.claude`.

### Per-dependency `targets:` (measured)

Hand-written `targets: [codex]` under the root entry, global `targets:
[claude, codex]`:

- **Bare `apm install -g -t claude,codex`.** The field works: the `.claude`
  copies are deleted (`Cleaned 5 stale … files`), and `~/.claude/skills` itself
  is removed. The lockfile records `target_subset: [codex]`.
- **Maestro's form** (CLI ref plus `--skill`, same ref, newer ref, or narrowed
  Selection). `targets:` is dropped from `apm.yml`, and both folders are written
  again. This confirms #1550's source reading, now measured.
- Why, on 0.35.0 (source): `apply_cli_skill_pin` carries the old `skills:` over,
  but not `targets:` (`install/package_resolution.py:285-322`). The new
  equality check keeps the old entry only when the requested entry is identical
  (`:485`), and the request has no `targets:`, so the entry is replaced
  (`:494`). `set_target_subset_for_entry` (`commands/_apm_yml_writer.py:28`)
  still has no caller.

So `targets:` could steer a whole Harness to one folder only if Maestro gave up
its CLI-ref install. It never gives one folder a different Selection or release.

### Remove (measured on 0.35.0)

`apm uninstall` still has only `--dry-run`, `-v` and `-g`
(`commands/uninstall/cli.py:247-262`). A named `-g` uninstall with
`targets: [codex]` deletes both folders' copies, the lockfile and both skills
folders.

## What changed 0.32.0 → 0.35.0 for Maestro's global deploy

The per-folder spikes gave the same disk and lockfile result on both versions.
These changes do touch the global deploy:

1. **A symlinked `HOME` deploys files now** (#2876, v0.33.0; measured). With
   `HOME` given as a symlink, 0.32.0 printed success and left four empty skill
   folders with no hashes. 0.35.0 wrote all six files and their hashes. LEARNINGS
   `apm-driver/symlinked-home-deploys-nothing` applies to ≤0.32.0 only.
2. **Output lines changed** (measured). The success markers Maestro matches
   (`apm-cli-driver.ts:30-45`) still print. Changed:
   - `Cleaned N stale files from <pkg>` now reads `Cleaned N stale deployed
     files for <pkg>` (#3120). Maestro does not parse it, but 0.32.0 fixtures
     carry the old line.
   - A narrowing install now also prints `[!] … Historical dependency claims
     retained: APM cannot confirm these paths belong to a current skill.` It
     prints with exit 0 and the success marker, also when nothing is left behind
     (#3315, `core/deployment_state.py:413-420`).
   - 0.32.0's false `1 skill replaced by a different package (last installed
     wins)` on a ref move is gone.
3. **A persisted `skills:` that matches nothing fails** (#3235). Before, it
   deleted every skill of the dependency and exited 0 (microsoft/apm#3204).
   Not measured here.
4. **Unmanaged collisions are checked before any write** (#3314, source and
   PR text). A differing unmanaged skill file now refuses the whole plan
   up front. On 0.32.0, apm wrote the other files first. Not measured.
5. **A skill folder is no longer deleted to replace it** (#3313, source and PR
   text). Members are copied one by one, and sibling files another owner holds
   survive. This may change the measured "same-ref install drops untracked
   files" (`docs/apm-behavior.md` § Update). Not measured.
6. **Legacy `.agents` rows are reconciled** (#3190). Rows with
   `target: legacy` are cleaned only when every `apm.yml` target is active.
   This changes a global lockfile last written by an apm older than the
   deployment ledger. Not measured.
7. **`CLAUDE_CONFIG_DIR`.** #3148 fixes MCP cleanup only; the skills root
   already followed the variable on 0.32.0 (1551 § 5). Two bugs filed against
   0.35.0 are open: an install into a second Claude profile deletes the
   default profile's skills (microsoft/apm#3423), and an uninstall there
   deletes the wrong profile's files (microsoft/apm#3425). One `~/.apm`
   lockfile tracks both profiles.

## Open questions

- Whether Maestro should ever install with one tool's `-t` while the global
  `apm.yml` declares two. ADR-0011 does this on a one-tool machine. Per the
  update spike, the other tool's copy then stays at an older release, while
  the lockfile and `apm outdated` name the newer one.
- Points 4–6 above: re-measure before the apm upgrade (`docs/agents/apm-upgrade.md`).
- microsoft/apm#3441 (open): an empty skill folder that already exists makes
  the install skip that skill with exit 0. Not checked against Maestro's
  guards.
