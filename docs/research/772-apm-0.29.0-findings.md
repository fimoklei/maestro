# apm 0.29.0 — measured findings (issue #772)

The runbook `docs/agents/apm-upgrade.md`, run 2026-09-04 against
`apm-cli==0.29.0` (installed via `uv tool install`), with `apm-cli==0.26.0` as
the control. Every `-g` command ran under a throwaway, `realpath`ed sandbox
`HOME`.

Steps 1–2 (measure, F1–F6) came from two sessions; steps 3–5 (source re-read,
the rewrite of `docs/apm-behavior.md`, the dependent sweep) and the removal
change (#775) from a third, which added F7–F11 below. **`docs/apm-behavior.md`
now describes 0.29.0**; this file keeps the measurements that drove it.

## Verdict

**0.29.0 is adopted.** F1 only fires when `HOME` passes through a symlink,
which the canary sandboxes did and a real home directory does not (see F1
§ Trigger). F3 — an edited *or added* file makes `apm uninstall` abort after
deleting the rest of the copy — is the one behaviour change the product had
to absorb: the removal use-case now refuses a diverged copy in front of apm,
as deploy and update already did, and names `Deploy again` as the way through
(#775; ruling in F3). The other findings changed fixtures, docs and wording
only. All four real-apm lanes are green on 0.29.0.

## Findings

### F1 — global install deploys nothing (blocking)

`apm install <ref> -g -t claude,codex` reports success, creates
`~/.claude/skills/<name>` and `~/.agents/skills/<name>`, and copies **no files
into them**. The global lockfile carries no `deployed_file_hashes` and no
per-file `deployed_files` rows.

Per-repo install is unaffected: files land, hashes are written.

Isolated against three variables — same ref, same tag, same sandbox shape:

| apm | ref | deployed files | `deployed_file_hashes` |
|---|---|---|---|
| 0.26.0 | `skills/tdd#v0.5.1` | 6 per tool | present |
| 0.29.0 | `skills/tdd#v0.5.1` | none | absent |
| 0.29.0 | `.apm/skills/tdd#v0.6.0` | none | absent |

Consequences for Maestro: a global deploy silently delivers nothing, and drift
has no baseline to compare against (`apm-driver.md` § Lockfile).

Now caught by two lanes, both of which asserted only that the directory existed
and so passed on 0.29.0 while it deployed nothing:

- `apm-global-install-canary.test.ts` asserts the deployed `SKILL.md` and the
  `deployed_file_hashes` key.
- the global half of `apm-uninstall-canary.test.ts` asserts the surviving
  skill's `SKILL.md`, not its directory.

Both failed on 0.29.0 and passed on 0.26.0 until the trigger below was found.

#### Trigger — a symlinked `HOME` (found 2026-09-04, follow-up session)

The defect needs `HOME` to contain a symlink component. Same ref
(`DietrichGebert/ponytail/skills/ponytail#2ed6c52c`), same apm 0.29.0, same
`-g -t claude,codex`:

| sandbox `HOME` | files deployed |
|---|---|
| `/private/tmp/…` (resolved) | yes |
| `/tmp/…` (symlink to `/private/tmp`) | no |

Cause, read from the installed source: `DeployableSourcePlan.create`
(`apm_cli/install/deployable_source_plan.py`) stores `source_root` resolved,
while `_integrate_native_skill` (`apm_cli/integration/skill_integrator.py`)
runs `shutil.copytree` over the unresolved `install_path` under `$HOME/.apm`.
`copy_ignore` then calls `relative_to` across the two, gets `ValueError`, and
ignores every entry. Per-repo installs resolve the project root first, which
is why only global scope fails. Confirmed by patching `copy_ignore` to log:
`dir=/tmp/…` against `root=/private/tmp/…`, `ignored=['SKILL.md']`.

The canary sandboxes came from `mkdtemp(join(tmpdir(), …))`, which on macOS
is `/var/folders/…` → `/private/var/…`. Both global lanes now `realpath` the
sandbox home and pass on 0.29.0 (four real-apm lanes green, 2026-09-04). The
product passes the ambient `HOME` through unchanged, and `/Users/<name>` holds
no symlink, so the cockpit's global deploy is not affected on a standard macOS
home. A user whose home directory is itself a symlink would hit it; Maestro
does not detect that case.

Still an upstream defect, not filed. No open microsoft/apm issue covers it;
apm#2744 (closed 2026-09-02) shares the missing counted-line symptom with a
different trigger.

### F2 — uninstall of an absent package exits 1

Was exit 0 on 0.26.0 with `[!] ... - not found in apm.yml`. Now exit 1:

```
[x] <ref> was not found in apm.yml. Run 'apm deps list' and retry with an installed package identifier.
[x] Uninstall aborted: 1 requested package(s) could not be selected. Resolve the errors above and retry; no changes were made.
```

The driver classifies on markers, not exit codes, and the success marker
`Uninstall complete: Removed N package(s) from apm.yml` is absent here, so the
fail-closed classification still holds. The `not found in apm.yml` substring
also still matches.

### F3 — a dirty deployed subtree now aborts the uninstall, after partial deletion

The repo's rule says a dirty deployed subtree warns and never blocks
(`apm-driver.md` § Remove). On 0.29.0 it blocks — and destroys most of the tree
first. With one deployed file edited locally:

```
Retained user-edited file .claude/skills/tdd/SKILL.md from <pkg>; resolve it and retry.
[i] Cleaned 12 stale files from <pkg>
[x] Uninstall could not remove tracked target files; package state was preserved.
[x]   - .claude/skills/tdd
[x]   - .claude/skills/tdd/SKILL.md
[x] Resolve or remove the listed files, then retry uninstall.
```

Exit 1. `apm.yml` and the lockfile keep the package. On disk only the edited
file survives; the other 11 deployed files across both tool directories are
already gone. So it is neither a clean abort nor a clean removal.

Widened in the third session, same setup, one variable each:

| deployed copy | uninstall |
|---|---|
| one file edited | aborts, exit 1, edited file retained, other 12 deleted |
| one untracked file added inside the skill dir | aborts, exit 1, the directory retained, other 13 deleted |
| one deployed file missing | completes, `Cleaned 13 stale files`, exit 0 |
| edited, then the retained file deleted, uninstall re-run | completes, exit 0 |

So apm's retention keys on a hash mismatch or an untracked entry, never on
absence, and the abort is recoverable only by removing what apm kept.

**Ruling (#774 → #775).** Maestro's classifier already reads every one of
these as `diverged`, so the removal use-case refuses that state before the
uninstall call — the same guard deploy and update have — instead of letting
the user consent to a deletion apm then leaves half done. The recovery the
notice names is `Deploy again`, which resets the copy (F7), then remove. The
"warn, never block" wording in `apm-driver.md` § Remove and the
`local-edits-will-be-lost` warning it described are gone; an unverifiable
copy (no recorded hashes) still warns and goes on consent, because apm's
behaviour on such a copy is unobserved. Letting apm abort and reporting the
partial deletion was rejected: the user would have agreed to "local edits
deleted too" and got neither that nor a clean refusal. Fixture:
`apm-uninstall-retained.txt`.

### F4 — uninstall no longer echoes the tag, and renamed its cleanup line

Success output names the package without its `#vX.Y.Z` suffix, and
`[+] Cleaned up N integrated skills` / `Removed N deployed skills file(s)` is
replaced by `[i] Cleaned N stale files from <pkg>`. The success marker itself is
unchanged. Nothing keys on the removed lines (`apm-driver.md` already forbids
parsing that count).

### F5 — install no-op wording changed

`(already in apm.yml)` became `(updated ref in apm.yml)`, plus a new
`[*] Updated apm.yml dependency entries` line. The no-op marker
`No changes -- install state already up to date` is unchanged.

### F6 — `apm view` auth failure reports a different git stderr

`fatal: could not read Username for 'https://github.com': terminal prompts
disabled` became `fatal: unable to get password from user`. Both classification
phrases (`Authentication failed`, `No token available`) still appear, so the
auth-required verdict is unaffected.

### F7 — a same-ref install still resets an edited or added file silently

Measured on the per-repo path with the F3 setups: `apm install <same ref>
-t claude,codex` over an edited `SKILL.md`, and again over an added
`EXTRA.md`, both print `(cached)` / `(files unchanged)` plus the no-op marker,
and both leave the subtree at the tag — the edit and the extra file are gone.
The uninstall protection of F3 does not extend to install. This is what makes
`Deploy again` the recovery for a refused removal.

### F8 — a narrowed `targets:` no longer orphans the other tool's copy

On 0.26.0, `targets: [claude]` in `apm.yml` over a `-t claude,codex` install
made `apm uninstall` delete only `.claude/skills/<name>` and drop the whole
lockfile entry. On 0.29.0 the same setup deleted both `.claude/skills/tdd`
and `.agents/skills/tdd` (`Cleaned 14 stale files`) and dropped the entry.
`targets:` scopes nothing; the rule against using it as a per-tool lever
stays for that reason instead of the orphaning one.

### F9 — lockfile `deployments[].target` names the deploy root

A `-t claude,codex` install writes `target: agents` for every `.agents/…`
row where 0.26.0 wrote `codex`. Entry keys are otherwise identical between
the two versions (diffed over all four lockfile fixtures); apm's entry model
declares optional fields a skill install leaves absent. Maestro's parse
needs no change; #172 cannot read `target` as a tool name.

### F10 — the install pre-flight probe is anonymous, and a throttled probe prints a line

`install/validation.py` probes a public repo anonymously before spending the
token, so a machine whose unauthenticated GitHub quota is spent prints `[i]
GitHub API rate limit hit while checking github.com; skipping the pre-flight
accessibility probe …` on every install and continues. With no token, the
failure then lands at the download step with `Authentication failed` / `No
token available` in the *install* output, a shape `apm-install-probes-failed.txt`
must not carry. The line matches no signal phrase. Nineteen captures in the
third session carried it before it was noticed (`LEARNINGS.md` ·
anonymous-probe-throttle-line).

### F11 — uninstall selection is all-or-nothing

`apm uninstall <installed> <absent>` prints the F2 error for the absent
package and `Uninstall aborted: 1 requested package(s) could not be selected
… no changes were made`, exit 1; the installed package stays. 0.26.0's
partial-success shape (success marker plus `Note: N package(s) were not
found`) cannot occur; the driver's not-found signals stay as a fail-closed
guard.

### Re-checks that changed nothing

A narrowing `-g -t claude` over a `-t claude,codex` home keeps every
`.agents` file and hash and leaves `targets: [claude, codex]` in
`~/.apm/apm.yml` (ADR-0013 holds). A bare `apm install <ref> -g` with no
`-t` writes `~/.agents/skills/<name>` only and leaves `~/.copilot`,
`~/.cache` and `~/Library` behind. The last dependency going deletes the
lockfile. `apm init -y` writes `apm.yml` alone. The `(source)` claims —
`_read_yaml_targets`, `declared_target_profiles`, `_is_stale`,
`resolve_targets`, `scope.py`, the ref parser's host gate, `compile`'s
overwrite and `--validate`'s empty error list, the absent 5000-token
constant — all re-read as unchanged; the ref parser gained a GitLab
heuristic for `prompts/instructions/collections` roots that never touches
`skills/`.

## The three hypotheses from the issue

**Uninstall's pre-state-mutation cleanup (upstream PR 2658).** Confirmed, and
worse than the hypothesis: it exits 1 and names retained paths, but only after
deleting every file it *could* remove. See F3.

**`--trust-bin` / `--no-trust-bin` (upstream PR 2508).** Both flags exist. No
warning line appeared in any of the 15 captures, because the skills under test
carry no `bin/` payload; the warning is conditional on one. No invocation turned
interactive — every capture ran non-TTY with no stdin and completed.

**The target catalog gained `grok-build` and `grok-cloud`.** Confirmed. The
reader count for `.agents/skills/` **did not move**: both new targets deploy to
`.grok/skills/`. Counted from the installed source
(`apm_cli/integration/targets.py`), 10 of the 15 targets with a skills mapping
resolve to `.agents/skills/`: copilot, cursor, opencode, gemini, antigravity,
codex, windsurf, agent-skills, openclaw, hermes. The comment in
`packages/core/src/deploy/deploy-tools.ts` stays correct.

`apm targets --json` in a repo holding only `.claude/` gained exactly one row,
`grok-build`; `grok-cloud` is not a project target.

## Unrelated defect found and fixed here

The three canary lanes resolved the harness's *latest* tag but installed via the
retired root `skills/<name>` subpath. That tree was dropped at v0.6.0, so all
four canary installs failed on 0.26.0 too — the lanes were red before this work
started, for a reason that has nothing to do with the apm version. They now use
the canonical `.apm/skills/<name>` (ADR-0021).

## How to reproduce

```bash
uv tool install "apm-cli==0.29.0" --force
MAESTRO_REAL_APM=1 GITHUB_TOKEN=$(gh auth token) GITHUB_APM_PAT=$(gh auth token) \
  pnpm test:integration
```

Every real-apm lane passes on both versions since the global sandboxes were
`realpath`ed (F1 § Trigger). To see F1 itself, drop the `realpath` in
`apm-global-install-canary.test.ts` on 0.29.0, or run any `-g` install with
`HOME` under `/tmp` on macOS.
